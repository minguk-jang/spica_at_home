# Qwen-AgentWorld 논문 분석 및 브라우저 에이전트 적용 보고서

## 1. 보고 개요

- 작성일: 2026-07-26
- 보고 목적: Qwen-AgentWorld 논문에서 배운 내용을 정리하고, 브라우저 에이전트의 테스트와 로직 개선에 적용할 수 있는 방법을 제안한다.
- 참고 논문: [Qwen-AgentWorld: Language World Models for General Agents](https://arxiv.org/pdf/2606.24597) (Qwen Team, arXiv:2606.24597v1)
- 적용 대상: 브라우저를 조작하고 여러 단계의 도구 호출을 수행하는 browser agent

이 보고서에서 말하는 “Qwen world model”은 논문의 정식 명칭인 **Qwen-AgentWorld**를 뜻한다. 논문은 이 모델을 Language World Model(LWM), 즉 에이전트의 행동을 입력으로 받아 환경의 다음 관측을 예측하는 언어 기반 세계 모델로 정의한다.

## 2. 한 줄 결론

Qwen-AgentWorld의 가장 중요한 시사점은 브라우저 에이전트의 테스트 루프에 별도의 환경 시뮬레이터를 두어, 실제 브라우저를 매번 실행하지 않고도 많은 상호작용을 반복하고 실패 상황을 의도적으로 만들 수 있다는 점이다. 다만 시뮬레이터는 실환경을 완전히 대체하는 검증기가 아니다. **시뮬레이터로 빠르게 탐색·회귀·적대적 시나리오를 돌리고, 실제 브라우저는 최종 품질 게이트로 유지하는 하이브리드 구조**가 적합하다.

## 3. 논문이 해결하려는 문제

일반적인 LLM 에이전트 연구는 현재 상태에서 어떤 행동을 선택할지, 즉 정책(policy)을 개선하는 데 집중해 왔다.

```text
정책:       상태(state)                 → 행동(action)
세계 모델:  상태(state) + 행동(action)  → 다음 상태/관측(next observation)
```

브라우저 에이전트에서는 클릭, 입력, 스크롤, 새 탭 열기 같은 행동이 URL, DOM, 접근성 트리, 로그인 상태, 네트워크 결과를 바꾼다. 이 다음 상태를 매번 실제 브라우저에서 확인하면 다음 문제가 생긴다.

- 브라우저·사이트·네트워크·인증 상태에 따라 실행 결과가 달라진다.
- 한 번의 테스트가 여러 도구 호출을 포함하므로 반복 비용이 크다.
- 결제, 삭제, 메일 전송처럼 실제 실행이 위험하거나 되돌리기 어려운 시나리오를 충분히 만들기 어렵다.
- 일반적인 정상 경로만 반복하게 되어, 에이전트의 취약한 예외 경로를 발견하기 어렵다.

논문은 정책만 학습하는 대신 환경의 동역학도 학습하자고 제안한다. 즉, “이 행동을 하면 환경이 어떻게 반응할 것인가?”를 모델 내부에서 예측하게 하여 시뮬레이션과 계획에 활용한다.

## 4. Qwen-AgentWorld의 핵심 구성

### 4.1 하나의 공통 상호작용 표현

논문은 MCP, 검색, 터미널, 소프트웨어 엔지니어링, Android, Web, OS의 7개 영역을 다음과 같은 공통 궤적 형식으로 통합한다.

```text
system_prompt = task_description
              + action_space
              + initial_state
              + demonstrations
              + simulation_instruction

trajectory = system_prompt + [(action_1, observation_1), ...,
                              (action_T, observation_T)]
```

LWM은 전체 프롬프트와 과거 상호작용, 현재 행동을 조건으로 다음 관측을 생성한다.

```text
predicted_observation_(t+1)
  = f(system_prompt, observations_≤t, actions_≤t)
```

브라우저 영역의 관측은 주로 **접근성 트리와 브라우저 상태**로 표현된다. 따라서 현재 browser agent가 DOM/접근성 기반으로 동작한다면 논문의 표현과 직접 연결하기 쉽다. 반대로 화면의 위치·색상·시각적 정렬 자체가 중요한 작업은 논문 범위만으로 충분하지 않으며, 스크린샷 또는 별도 비전 모델을 함께 사용해야 한다.

### 4.2 CPT → SFT → RL의 3단계 학습

논문의 표현을 요약하면 다음과 같다.

1. **CPT(Continual Pre-Training)**: 환경의 상태 전이, 도구 동작, 전문 지식을 주입한다.
2. **SFT(Supervised Fine-Tuning)**: 다음 상태를 예측하는 사고 패턴을 명시적으로 활성화한다. 같은 행동이라도 이전 상태와 긴 상호작용 문맥에 따라 결과가 달라짐을 학습한다.
3. **RL(Reinforcement Learning)**: 예측 결과의 형식, 사실성, 턴 간 일관성, 현실성, 완성도를 평가해 시뮬레이션 충실도를 다듬는다.

RL 보상은 LLM 심사 기반 5차원 루브릭과 실행 가능한 규칙 검증기를 함께 사용한다. 루브릭만 사용하면 그럴듯한 설명이나 자기 칭찬으로 보상을 해킹할 수 있으므로, URL·JSON 스키마·상태 플래그처럼 결정 가능한 부분은 규칙 검증기로 고정한다. 또 여러 턴을 단순히 모두 RL 샘플로 확장하면 공통 접두어가 겹쳐 학습이 붕괴할 수 있어, RL 단계에서는 궤적당 한 턴을 사용해 안정성을 확보했다.

### 4.3 AgentWorldBench 평가 방식

논문은 9개 기존 에이전트 벤치마크에서 5개 프런티어 모델이 실제 환경과 상호작용한 궤적을 수집하고, 그 결과를 LWM 평가 데이터로 변환했다.

| 항목 | 규모/내용 |
|---|---|
| 도메인 | MCP, Search, Terminal, SWE, Android, Web, OS 등 7개 |
| 평가 샘플 | 턴 단위 2,170개 |
| 원천 벤치마크 | 9개 |
| 실제 궤적을 만든 모델 | 5개 프런티어 모델 |
| 평가 차원 | Format, Factuality, Consistency, Realism, Quality |
| 기준 관측 | 모든 샘플에서 실제 환경 실행 결과를 정답으로 사용 |

첫 턴, 중간 턴, 마지막 턴을 함께 평가하여 초기 상태부터 긴 문맥 누적에 따른 오류까지 확인한다. 결정적인 출력은 정확히 맞춰야 하고, 실행마다 달라질 수 있는 PID·타임스탬프 같은 값은 형식과 범위 중심으로 평가한다. 이 구분은 브라우저 테스트에도 그대로 적용할 수 있다.

## 5. 논문의 주요 결과

### 5.1 세계 모델 자체의 시뮬레이션 품질

Qwen-AgentWorld-397B-A17B의 AgentWorldBench 전체 평균은 58.71점으로 GPT-5.4의 58.25점보다 높았다. 다만 GUI(Web, Android, OS)에서는 멀티모달 사전학습의 이점을 가진 모델들이 강했고, Qwen-AgentWorld가 모든 영역에서 최고였던 것은 아니다. 35B-A3B 모델은 동일 계열의 기본 모델 대비 전체 평균이 47.73점에서 56.39점으로 8.66점 상승했다.

이 결과는 “세계 모델 학습이 일반 능력의 단순한 증가”라기보다, 행동 이후 상태를 예측하고 긴 상호작용의 상태를 유지하는 능력을 별도로 강화한다는 근거로 해석할 수 있다.

### 5.2 시뮬레이터로 에이전트를 학습한 결과

Qwen-AgentWorld를 정책 모델과 분리된 환경 시뮬레이터로 사용했을 때 다음과 같은 결과를 보고했다.

| 적용 방식 | 결과 |
|---|---:|
| 4천 개 OpenClaw 시뮬레이션 환경, Claw-Eval | 65.4 → 69.7, +4.3 |
| 4천 개 OpenClaw 시뮬레이션 환경, QwenClawBench | 47.9 → 55.0, +7.1 |
| 제어 없는 Sim RL, Tool Decathlon | 32.4 → 31.5, 오히려 하락 |
| 제어 지시가 있는 Sim RL, Tool Decathlon | 32.4 → 36.1, +3.7 |
| 제어 지시가 있는 Sim RL, MCPMark 평균 | 21.5 → 33.8, +12.3 |
| 가상 검색 세계, 35B WideSearch F1(Item) | 34.02 → 50.31, +16.29 |
| 가상 검색 세계, 35B WideSearch F1(Row) | 13.72 → 24.21, +10.49 |

핵심은 단순히 실제 환경을 흉내 내는 것이 아니라, “검색 결과를 일부만 보여 주기”, “한 번은 API 오류를 반환하기”, “페이지 추출을 추가로 호출해야만 완전한 정보를 주기”처럼 에이전트의 약점을 겨냥한 조건을 넣었다는 점이다. 통제되지 않은 시뮬레이션은 신뢰할 수 있는 학습 신호를 만들지 못했지만, 통제 가능한 시뮬레이션은 실제 환경 학습보다 더 강한 행동 변화를 만들었다.

### 5.3 하나의 모델 안에서 세계 모델과 에이전트를 통합한 결과

세계 모델 학습을 먼저 수행한 뒤 별도의 에이전트 미세조정 없이 평가했을 때도 성능이 올랐다. 예를 들어 WideSearch F1(Item)은 33.38에서 46.17(+12.79), Terminal-Bench 2.0은 33.25에서 39.55(+6.30), Claw-Eval은 53.60에서 64.88(+11.28)로 개선됐다. 에이전트가 실제 행동 전에 다음 환경 응답을 예측하는 비율의 정확도도 69.9%에서 78.3%(+8.4%)로 상승했다.

따라서 LWM은 단순한 “가상 브라우저”가 아니라, 에이전트가 행동을 실행하기 전에 결과를 머릿속으로 점검하는 **미래 지향적 reflection**으로도 볼 수 있다.

## 6. 우리 browser agent에 적용했을 때의 배움

### 배움 1: 테스트 단위는 “작업 성공/실패”가 아니라 상태 전이여야 한다

현재 테스트가 최종 성공 여부만 기록하면 어느 클릭 이후 상태가 잘못되었는지 찾기 어렵다. 각 턴을 다음처럼 기록해야 한다.

| 구분 | 브라우저 예시 |
|---|---|
| 초기 상태 | URL, 탭, 로그인/권한 상태, 쿠키 요약, 뷰포트, 주요 DOM/접근성 트리 |
| 행동 | navigate, click, type, select, scroll, keypress, wait, tab 전환 |
| 다음 관측 | URL/제목, 접근성 트리, 표시 텍스트, 활성·비활성 요소, 팝업/새 탭, 오류 |
| 결과 판정 | 목표 조건 충족, DOM 변화, 네트워크 오류, 안전 정책 위반, 소요 시간 |

이 구조가 있어야 같은 행동을 실제 브라우저와 LWM 양쪽에 넣고, 다음 관측의 차이를 비교할 수 있다.

### 배움 2: “그럴듯한 환경”보다 “약점을 재현하는 환경”이 테스트에 유용하다

브라우저 에이전트의 실패는 정상 페이지보다 경계 조건에서 많이 발생한다. 시뮬레이터에 다음과 같은 자연어 제어 지시를 넣으면 재현 가능한 적대적 회귀 테스트를 만들 수 있다.

- 클릭 직후 요소가 stale 상태가 되고 DOM이 한 번 갱신된다.
- 검색 결과는 첫 페이지에 일부만 반환하고, 완전한 내용은 상세 페이지에서만 제공한다.
- 세 번째 턴에 세션이 만료되어 재로그인이 필요하다.
- 동일한 버튼 라벨이 두 개 존재해 접근성 이름과 주변 문맥을 함께 봐야 한다.
- 네트워크 429 또는 일시적 타임아웃이 한 번 발생한 뒤 재시도하면 성공한다.
- 새 탭 또는 팝업이 열리지만 원래 탭의 상태도 보존해야 한다.
- 제출 직전에는 실제 실행 대신 확인 단계로 멈춰야 한다.

이러한 시나리오는 실제 서비스에서 무작위로 기다리지 않고도 반복할 수 있어, agent logic의 약점을 빠르게 좁히는 데 적합하다.

### 배움 3: 접근성 트리는 좋은 시작점이지만 모든 브라우저 테스트를 대표하지 않는다

논문의 Web 도메인은 접근성 트리와 브라우저 상태를 사용한다. 따라서 요소 찾기, 페이지 이동, 폼 입력, 텍스트 추출처럼 구조화된 브라우저 작업은 빠르게 적용할 수 있다. 그러나 CSS 위치, 겹침, 색상 대비, 캔버스, 드래그 정밀도, 이미지 속 텍스트처럼 픽셀 정보가 필요한 테스트는 별도의 스크린샷/비전 경로가 필요하다.

### 배움 4: 시뮬레이터 품질을 먼저 검증해야 한다

시뮬레이터가 만든 오류를 에이전트의 오류로 착각하면 잘못된 로직을 학습할 수 있다. 논문처럼 실제 브라우저에서 얻은 정답 관측을 보류 데이터로 두고 다음을 분리해서 평가해야 한다.

1. 월드 모델이 같은 행동 뒤의 다음 상태를 얼마나 정확히 예측하는가?
2. 그 시뮬레이터로 학습/튜닝한 에이전트가 실제 브라우저에서도 좋아지는가?

첫 번째 게이트를 통과하지 못한 시뮬레이터는 두 번째 목적에 바로 사용하지 않는다.

## 7. 제안하는 적용 구조

```text
                         ┌──────────────┐
                    ┌───▶│ 실제 브라우저 │───┐
                    │    └──────────────┘   │
브라우저 에이전트 ──┤                         ├──▶ 다음 관측
   (정책/행동)      │    ┌──────────────┐   │
                    └───▶│ Qwen-AgentWorld│───┘
                         │  (시뮬레이터)   │
                         └──────────────┘
                              ▲
        궤적 기록·정규화·제어 지시·규칙 검증·sim/real 비교
```

### 7.1 1단계: 브라우저 궤적 스키마와 기록기 구축

먼저 학습보다 기록 형식을 고정한다. 한 턴의 최소 예시는 다음과 같다.

```json
{
  "task_id": "checkout-001",
  "turn": 3,
  "state": {
    "url": "https://shop.example/cart",
    "tab_id": "tab-0",
    "accessibility_tree": "...",
    "visible_text": "...",
    "session_summary": "authenticated"
  },
  "action": {
    "type": "click",
    "target": {"role": "button", "name": "결제하기"}
  },
  "observation": {
    "url": "https://shop.example/checkout",
    "accessibility_tree": "...",
    "dom_diff": "...",
    "error": null
  },
  "ground_truth": {
    "task_success": false,
    "expected_transition": "checkout_page"
  }
}
```

비밀번호·토큰·개인정보는 원문으로 저장하지 않고 마스킹한다. 쿠키나 서버 데이터 전체를 복제하기보다, 테스트에 필요한 초기 상태와 성공 조건을 별도로 선언하는 것이 안전하다.

### 7.2 2단계: 실제 궤적 기반의 오프라인 예측 평가

실제 브라우저에서 수집한 궤적을 학습 데이터와 보류 평가 데이터로 나눈다. 각 평가 턴에서 같은 `state + action`을 Qwen-AgentWorld에 넣고 다음 관측을 생성한다.

브라우저에 맞춘 평가 항목은 다음과 같이 구성한다.

| 평가 항목 | 판정 방법 |
|---|---|
| 구조 | JSON/접근성 트리/도구 응답 스키마가 파싱되는가 |
| 결정적 상태 | URL, 탭 수, 리다이렉트, 성공 플래그, 특정 텍스트를 exact match |
| 요소 상태 | 목표 요소의 존재·이름·역할·활성 상태를 비교 |
| 오류 동작 | timeout, 429, stale element, auth 만료 등 오류 유형과 재시도 가능성을 비교 |
| 턴 간 일관성 | 이전 클릭·입력·탭 전환이 다음 턴에도 유지되는가 |
| 동적 값 | 타임스탬프·세션 ID는 형식/범위만 검증 |

이 단계의 기준은 “평균 점수 하나”가 아니라, deterministic verifier와 의미 기반 평가를 함께 두는 것이다. 논문의 Format·Factuality·Consistency·Realism·Quality 루브릭은 상위 평가에 사용하고, URL·DOM 상태·성공 조건은 규칙 검증기로 고정한다.

### 7.3 3단계: 제어 가능한 시나리오 생성

예측 품질이 확인되면 테스트용 시뮬레이션 지시를 추가한다. 정상 시나리오를 복제하는 데 그치지 않고, 한 번에 한 가지 취약점을 자극하도록 시나리오를 설계한다.

- 탐색/셀렉터: 동적 ID, 중복 라벨, lazy loading, iframe, 새 탭
- 상태/세션: 로그인 만료, 권한 변경, 장바구니 상태 초기화, 뒤로 가기
- 네트워크: 지연, 429, 5xx, 부분 응답, 재시도 후 성공
- 정보 탐색: 검색 결과 일부 누락, 페이지네이션, 상세 페이지 추가 호출
- 안전: 삭제·결제·전송 직전 확인 요구, 권한 상승 요청 거부

각 시나리오에는 예상되는 최종 상태와 통과 조건을 함께 둔다. 이렇게 하면 에이전트가 시뮬레이터의 문장 스타일을 외우는 대신, 실제로 필요한 재시도·검증·중단 행동을 학습했는지 확인할 수 있다.

### 7.4 4단계: 시뮬레이터 우선, 실제 브라우저 최종 게이트

개발 루프에서는 시뮬레이터를 우선 사용한다.

1. 새 agent logic을 시뮬레이터에서 여러 초기 상태와 예외 조건에 대해 빠르게 반복한다.
2. 실패한 궤적과 상태 전이를 회귀 테스트 세트로 저장한다.
3. 변경사항이 없는 안정적인 케이스와 위험도가 낮은 케이스는 시뮬레이터로 매 커밋 검증한다.
4. 브라우저 버전, 실제 CSS/렌더링, 인증, 네트워크, 보안·권한, 비가역 동작은 실제 브라우저에서 최종 검증한다.

이 구조는 “실제 테스트를 없애는 것”이 아니라, 실제 테스트를 가장 정보 가치가 높은 케이스에 집중시키는 방식이다.

### 7.5 5단계: 행동 전 예측을 agent logic에 연결

모델을 바로 재학습하지 않아도 다음과 같은 reflection 단계를 실험할 수 있다.

```text
1. 현재 상태와 후보 행동을 확인한다.
2. 행동 후 예상 URL/요소/오류/다음 상태를 짧게 예측한다.
3. 예상 상태가 목표·안전 정책과 충돌하면 행동을 수정하거나 중단한다.
4. 실행 후 실제 관측과 예측을 비교해 다음 행동에 반영한다.
```

논문에서 LWM RL 이후 실제 궤적의 다음 환경 응답 예측 정확도가 69.9%에서 78.3%로 높아지고, Postfix 사례에서 실행 전에 잘못된 설정 경로를 제거한 것처럼, 이 단계는 불필요한 클릭·재시도·탐색을 줄일 가능성이 있다. 단, 이 예측은 안전 판단의 보조 신호이며 실제 실행 결과보다 우선해서는 안 된다.

## 8. 실험 설계 제안

첫 실험은 큰 모델을 새로 학습하는 프로젝트보다, 브라우저 한정의 작은 검증으로 시작하는 것이 좋다.

### 비교군

1. **Real-only**: 실제 브라우저 궤적만 사용한다.
2. **Uncontrolled Sim**: 제어 지시 없이 시뮬레이터를 사용한다.
3. **Controlled Sim**: stale element, 부분 응답, 세션 만료 등 목표 실패 모드를 명시한다.
4. **Hybrid**: 시뮬레이터로 반복한 뒤 보류된 실제 브라우저 세트에서 검증한다.

모든 비교군은 같은 정책 체크포인트와 겹치지 않는 실제 테스트 세트를 사용한다. 논문의 결과처럼 uncontrolled Sim이 실제로는 개선을 만들지 못할 수 있으므로 Controlled Sim과 반드시 분리해야 한다.

### 측정 지표

- 실제 브라우저 task success rate
- 시도한 action 수와 불필요한 retry 수
- 오류 유형별 복구율
- 평균 테스트 시간과 외부 서비스 호출 수
- 상태 전이 예측의 구조적 유효성 및 결정적 필드 정확도
- 시뮬레이터와 실제 브라우저의 실패 순위 일치도
- 긴 궤적에서의 누적 상태 divergence
- 안전 위반(확인 없는 제출, 잘못된 탭 조작, 비인가 데이터 노출) 수

성공 기준은 먼저 단순 복사/규칙 기반 baseline보다 시뮬레이터 예측이 나은지 확인하고, 그 다음 시뮬레이터로 개선한 정책이 보류 실제 테스트에서 성능 저하를 만들지 않는지 확인하는 순서로 둔다.

## 9. 현실적인 도입 순서

### 바로 적용할 수 있는 범위

- DOM/접근성 트리 기반 클릭·입력·탐색 회귀 테스트
- 정적 테스트 fixture에서의 페이지 이동·폼·검색·페이지네이션
- timeout, 429, stale element, 부분 응답 같은 예외 시나리오
- 행동 전 예상 상태를 생성하는 reflection 프롬프트
- 실제 궤적과 시뮬레이션 궤적을 비교하는 오프라인 evaluator

### 나중으로 미뤄야 하는 범위

- 픽셀 단위 레이아웃·시각 회귀·드래그 정밀도
- 실제 결제·삭제·메일 발송처럼 비가역적인 동작
- 인증·CAPTCHA·보안 정책이 핵심인 프로덕션 플로우
- 최신 외부 웹 콘텐츠의 사실성 보장

초기 모델은 개발 반복을 위한 35B-A3B 계열을 우선 검토하고, 더 높은 충실도가 필요한 오프라인 검증에서 397B-A17B 계열을 비교하는 방향이 합리적이다. 단, 실제 사용 가능 여부·가중치 공개·라이선스·추론 비용은 도입 시점에 별도로 확인해야 한다. 논문의 모델 크기와 학습 데이터 규모를 그대로 재현하는 것은 우리 팀의 첫 목표가 되어서는 안 된다.

## 10. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 시뮬레이터가 그럴듯하지만 틀린 DOM/응답을 생성 | 실제 궤적 보류 세트, 결정적 검증기, sim-to-real 게이트 |
| 여러 턴에서 작은 오류가 누적되어 상태가 발산 | 매 턴 URL·탭·요소 ID를 검증하고 divergence 시 실제 브라우저로 전환 |
| 시뮬레이터 특유의 문장/오류 패턴을 정책이 암기 | 여러 프롬프트 템플릿·초기 상태·오류 표현을 사용하고 실제 사이트를 보류 |
| 인증 정보나 개인정보가 학습 데이터에 포함 | 토큰·쿠키·개인정보 마스킹, 최소 상태만 저장, 합성 fixture 우선 |
| 텍스트 관측이 시각적 문제를 놓침 | 접근성 트리 경로와 스크린샷/비전 경로를 분리하고 최종 GUI 테스트는 실환경에서 수행 |
| LLM 심사 보상 해킹 | JSON/URL/성공 조건은 규칙 보상으로 고정하고 심사 루브릭은 보조로 사용 |
| 최신 웹 변화 반영 실패 | 웹 지식의 사실성보다 상태 전이·행동 전략을 학습하고 최신성은 실제 브라우저에서 검증 |

## 11. 최종 판단 및 다음 액션

이 논문에서 얻은 가장 실용적인 교훈은 “브라우저 에이전트를 더 강한 모델 하나로만 개선하지 말고, 행동 이후의 환경 반응을 예측하는 별도 학습·테스트 축을 만든다”는 것이다. Qwen-AgentWorld는 우리 browser agent에 다음 세 가지 방식으로 접목할 수 있다.

1. 실제 브라우저를 반복 실행하기 전에 수천 개의 상태 전이를 시뮬레이션하는 **빠른 회귀 테스트기**
2. stale element, 부분 검색 결과, 세션 만료처럼 실제에서 드문 실패를 의도적으로 만드는 **제어 가능한 적대적 테스트 생성기**
3. 행동 실행 전 예상 결과를 확인해 불필요한 클릭과 재시도를 줄이는 **미래 상태 기반 reflection 모듈**

권장하는 다음 액션은 아래와 같다.

1. 현재 browser agent의 action/observation 로그를 위의 공통 스키마로 정규화한다.
2. 개인정보를 제거한 실제 브라우저 궤적을 모아, 먼저 다음 상태 예측 정확도를 측정한다.
3. DOM/접근성 기반의 작은 Web 평가 세트를 만들고, 정상·예외·긴 문맥 케이스를 분리한다.
4. uncontrolled Sim과 controlled Sim을 비교해 제어 지시가 실제로 어떤 실패 복구 행동을 만드는지 확인한다.
5. 시뮬레이터에서 좋아진 정책을 반드시 보류된 실제 브라우저 세트에 통과시킨 뒤, 그 결과가 확인될 때만 개발 회귀 루프에 편입한다.

결론적으로 Qwen-AgentWorld는 브라우저 에이전트의 실제 테스트를 없애는 기술이 아니라, **실제 테스트로 가기 전의 반복·탐색·실패 시나리오 생성 비용을 낮추고 agent logic의 개선 주기를 짧게 만드는 기술**로 보는 것이 정확하다. 우리 업무에는 “시뮬레이터 우선 개발 + 실제 브라우저 최종 게이트”가 가장 안전하고 효과적인 도입 방식이다.
